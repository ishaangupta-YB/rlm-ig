An engine for recursive language models · Python 3.11+ · MIT

The model never reads your data. It writes code that does.

rlm-ig puts your data in a live Python process as a variable called context. The model sees a short description of it, writes one code block per turn, sees what the code printed, and repeats until it calls submit(answer). Code does the exact work. Cheaper model calls read the pieces the code picked out. Pieces that are still too big go to sub-agents with their own Python process.

Why it exists

The problem it solves

A model handed a large log either cannot fit it or reads it badly. Exact questions (counts, top-N, joins) are the worst case, because reading is the wrong tool for counting.

Every follow-up question sends the log again unless the provider caches it. A 3.7 MB file (the README's CLI test) would be roughly 900,000 tokens and does not fit at all.

The core trade

A plain call spends tokens to read data once, in one pass, and answers immediately. rlm-ig spends extra turns (each one a round trip of 1 to 3 seconds) to avoid reading most of the data at all. That trade pays off when the data is large and the question can be answered by code. It loses when the data is small or the question needs every word read.

Architecture

Architecture map

Four layers: an entry layer (Python API, CLI, sessions), the engine (one shared Run, one Agent per agent), the sandbox (a host proxy plus a worker subprocess), and pluggable model backends. Events fan out to the console, the JSONL trace and your callback.

Engine and Run

api.py · engine/run.py

Engine resolves models once and can be reused (sessions do). Run is per question: it owns the ledger, the two semaphores, the temporary work directory (rlm-run-*/agent-<id>) and the three model entry points: turn for agent turns, ask and ask_batch for sub-model calls.

Agent

engine/agent.py

The loop and the call server. It extracts code from each reply, runs it, formats what came back, validates submissions against the schema, and handles calls that the running code makes back into the host. It also enforces depth, the pass-through guard and slot handover for children.

Prompts

engine/prompts.py

Every word the model sees. One fixed system prompt for all agents (so a provider can cache it across the tree), an opening message built per agent, an observation format with a turn footer, and the wrap-up texts LAST_CALL and BUDGET_SPENT.

Sandbox and worker

sandbox/host.py · sandbox/worker.py

The host side spawns the worker, ships it its own source over stdin, frames JSON messages, enforces cell_timeout and replaces a dead worker. The worker holds the namespace and the REPL helpers and asks the host for every model or tool call.

Backends

models/*.py

A Model hands out Chat objects with one method that matters: send(text) → Reply. HTTP backends keep history in-process (StatelessChat); Claude Code and opencode keep it inside the external agent's session and only receive the new message.

Support modules

schema.py · text.py · tools/ · trace/ · loaders.py

A small JSON Schema validator with no dependencies, code extraction and repair, tool wrapping and an MCP client (stdio and HTTP), JSONL trace writer with terminal and HTML viewers, and file loaders (.json, .jsonl, .csv, .tsv, directories).

Control flow

A run, step by step

This is the order things happen in when you call rlm.run(task, context). File references point at main.

  1. Configuration. Config.load() layers defaults, the user config, the nearest rlm.toml, RLM_* environment variables and your keyword arguments. With no model set, detect() picks Claude Code if claude is on PATH, then opencode, then the Anthropic API if a key and the SDK exist. config.py · models/__init__.py
  2. Engine and Run. The Engine resolves model and sub_model (the same object if equal), connects MCP servers if any, and builds the event sinks. A fresh Run gets a Ledger with your limits and two semaphores sized to max_parallel or the smaller backend default (4 for Claude Code, 8 for APIs). api.py:114 · engine/run.py:24
  3. Worker start. The root Agent asks the run for a sandbox. The host starts python -u -c <bootstrap> <n>, writes the worker's own source (about 32 KB) as the first bytes on stdin, then an init frame with the encoded context, tool signatures and settings. The worker builds its namespace and answers ready with a structural summary. About 50 ms locally. sandbox/host.py:219
  4. The opening message. The model gets one message: ## Task, ## Data (the summary, never the data), optional ## Earlier in this session, ## Tools, ## Answer format, and ## Limits. engine/prompts.py:118
  5. Turn. Run.turn() reserves one call in the ledger, waits for a request slot, sends, records tokens and cost, and emits model.reply. engine/run.py:84
  6. Extract code. The engine takes fenced blocks tagged python (also py, python3, repl, ipython, pycon), joins them, and repairs common damage if the result would not compile. No code means "nothing ran" and the turn is spent. text.py:110
  7. Run the cell. The host sends an exec frame. While the cell runs, the worker may send call frames (ask, delegate, tools); the host serves each one concurrently and answers with a reply frame. The cell ends with a done frame carrying stdout, any traceback, and whether submit was called. sandbox/host.py:280
  8. Observe. Output is cut to 8,000 characters (60% head, 40% tail) and a footer like [turn 2 of 20 · 0.0s] is added. Near the end the footer counts down the remaining turns. engine/prompts.py:169
  9. Submit. submit(value) raises a private exception inside the cell, so nothing after it runs. The value is reduced to JSON, validated against your schema, and either returned or sent back with the validation errors. sandbox/worker.py · engine/agent.py:187
  10. Result. The engine fills a Result with answer, status (ok, partial, failed), usage per model, step and agent counts, seconds, trace path, and parsed (an instance of your dataclass or Pydantic model). Temporary directories are removed. api.py:143
Data flow

Inside the REPL worker

The worker is a plain Python process talking to the host over its stdin and stdout. Messages in both directions are an ASCII length, a newline, then that many bytes of UTF-8 JSON.

Bootstrap: nothing installed on the far side

The command line is [launcher…] python -u -c BOOTSTRAP <len>. The bootstrap is seven lines that read exactly len bytes from fd 0 with unbuffered os.read and exec them. That is the whole worker. Because the source travels over stdin, the same worker runs unchanged inside docker run -i, a jail, or a remote shell, with nothing mounted. The read is exact on purpose: a buffered reader would swallow the first protocol frames.

sandbox/host.py:31

File descriptors: the protocol cannot be corrupted

On start the worker duplicates fds 0 and 1 into private protocol streams, points fd 0 at /dev/null, and points fds 1 and 2 at a pipe that a pump thread copies into the capture buffer. So print, C extensions and child processes all land in the cell output and none of them can write into the protocol. A sync marker flushes the pipe before each done.

sandbox/worker.py · main(), _pump()

The trust rule

Host to worker may carry pickles (a non-JSON context, a non-JSON tool result), because the host is the trusted side. Worker to host is always JSON: values pass through jsonable(), which unwraps dataclasses, Pydantic models, numpy arrays and dates and degrades anything else to repr. The host never unpickles or evals what a worker sends.

sandbox/host.py:encode · worker.py:jsonable

Output capture

The worker keeps the first and last 200,000 characters of a cell's output (capture_limit) and drops the middle with a marker. The host then clips to output_limit (8,000) before the model sees it. The last expression of a cell is echoed with a compact repr, as in a notebook: 30 list items, 600-char strings.

Sub-calls

ask, ask_map and automatic batching

ask is for work that only needs reading: classify this record, extract fields from this chunk. delegate is for work that needs exploring. The engine batches ask_map on its own, which is one of the most useful things in the codebase.

When the model calls ask_map(prompt, items) with one prompt and a list of items, Agent._batches() groups them before any request goes out:

  • The data budget per call is min(ask_batch_chars, ask_limit − len(prompt) − 2000), so 24,000 characters by default.
  • Each item costs its length plus 40 characters of wrapper.
  • An item larger than half the budget (12,000) gets a call to itself, so a big chunk is never diluted by neighbours.
  • A group closes at 16 items (ask_batch) or when the next item would overflow the budget.
  • The batched prompt wraps items in <item index="n"> tags and demands a JSON array of exactly n elements. A malformed reply gets one repair call; if that fails too, the group falls back to one call per item and a note event records it.

The README's measured example: 300 support tickets (350 KB) classified into 4 categories took 22 calls and 23 seconds with 296 of 300 correct. With ask_batch=1 the same job took over three minutes and ran into the 300-call limit, for roughly the same accuracy.

Recursion

Sub-agents and depth

A sub-agent is the same Agent class one level down. It shares the run's ledger and concurrency pools, gets a fresh REPL, and cannot see its parent's variables.

Depth. The root is level 0. max_depth (default 2) is how many levels may exist below it. At the deepest level delegate raises DelegationRefused, and the agent's opening message already says so in its Limits section. ask and ask_map still work there.

Two concurrency pools. request_slots caps requests in flight; agent_slots caps live sub-agents. When an agent starts children it gives its own agent slot back while it waits, and takes it back afterwards (Agent._spawn). Without that handover, a tree deeper than the pool size would deadlock: every slot would be held by a parent waiting on a child that can never start.

The pass-through guard. If a parent holds at least 20,000 characters and calls delegate with data that is 80% or more of that, the call is refused with "this only moves the problem down a level". The model must narrow the data first or pass whole=True. It applies to delegate, not delegate_map.

Tools in children. Sub-agents inherit the parent's tools unless tools=[...] names a subset. A function the model wrote itself can be passed too: its source is copied into the child's REPL as a helper, so it must be self-contained.

Failure travels up. A child that runs out of turns or budget raises inside the parent's cell as SubcallError. In delegate_map, a failed child becomes a Failed(...) entry; only if every child fails does the call raise.

Read the cost number carefully

Claude Code reports a figure even under a subscription. It is the API-equivalent price, not a charge to you, so max_usd caps a hypothetical bill there. Backends that report only tokens get an estimate from models/pricing.py or your [pricing] table; with neither, max_usd cannot apply, and the engine emits a note saying so.

Why one fixed system prompt matters

Every agent in a tree, root and sub-agents, gets the identical 4,070-character SYSTEM string. Everything that varies (task, data summary, tools, schema, limits, depth) goes in the first user message. On a provider that caches by prefix, the system prompt is paid for once and read from cache by every other agent in the run.

Model choice is the main cost lever

The root decides what to do and writes code; sub-models only read. model="claude-code:sonnet", sub_model="claude-code:haiku" is the README's first recommended optimisation. Pricing for estimates lives in models/pricing.py and can be overridden per model under [pricing].

State

Sessions

A Session keeps the root's REPL alive across questions, so the second question can reuse what the first one parsed.

Each task starts a fresh model conversation. The only memory is the live namespace plus a short record: the last 8 tasks with one-line answers and an inventory of up to 60 variables. That keeps the prompt small however long the session runs.

With path=, after every task the worker pickles each user variable (up to 50 MB each) and the source of every function or class the model defined, and the session writes them atomically to a JSON file. Opening the same path restores them. Open files, locks and generators are skipped and listed.

A session file holds pickles made by the worker. Restoring one unpickles it inside a worker, so treat a session file as code and never restore one from someone you do not trust.

The CLI equivalent is rlm "…" --session NAME, stored under ./.rlm/sessions or RLM_SESSION_DIR.

Traces go to ~/.local/state/rlm-ig/traces/<timestamp>-<task-slug>.jsonl. rlm trace replays the last one as an agent tree, --full shows every code block and output, and --html OUT writes a self-contained page.

on_event= receives the same events live, which is the hook for metrics, progress bars or shipping traces to your own store.

Traces contain your data

Cell outputs and model replies are written verbatim (clipped to the output limit). If the data is sensitive, set trace = false or put trace_dir somewhere with the same retention rules as the data.

Threat model

Security model

By default the worker is an ordinary subprocess running as you. It is not a security boundary, and the docs say so plainly.

Default: subprocess

  • Can read your files, use the network, start programs
  • Environment scrubbed to an allowlist (PATH, HOME, locale, proxies, CA bundles…). API keys are not passed
  • Throwaway working directory, not a jail
  • Optional memory_mb sets RLIMIT_AS

--sandbox docker

  • --network none, read-only root, tmpfs /tmp
  • --cap-drop ALL, no-new-privileges
  • --memory 1g --pids-limit 256, user 65534
  • Image: Python 3.12 + numpy, pandas, dateutil, regex. Covered by tests against a real Docker daemon in CI

What still runs on the host

  • ask, delegate, and your tools cross the container boundary by design
  • A tool that runs SQL or shell on the model's say-so is as dangerous as the model's code
  • MCP servers have your full environment
  • Text in the data can steer the model (prompt injection)

The honest question

Does it save anything, or is it hype?

It saves a lot on one class of problem and costs more on others. The approach is sound; the marketing around "infinite context" is not.

Clear win

  • Data far larger than the window: logs, exports, document sets in the MB range
  • Questions code can answer exactly: counts, rankings, joins, "which X happened twice"
  • Many items that each need a short judgement: ask_map batches 300 tickets into about 19 calls
  • You need to show how an answer was produced

Depends

  • Medium documents (50k to 150k tokens) that fit in a modern window: a plain call is faster; rlm-ig is more exact on numbers
  • Summaries of a whole document: ask_map over chunks reads everything anyway, plus orchestration overhead
  • Root model quality: a weak coder wastes turns, and every turn is a round trip

Loses

  • Small inputs: 2+ calls and a ~1k-token system prompt where one call would do
  • Low-latency paths (chat replies, per-request triage): seconds to minutes per answer
  • Questions needing subtle cross-document reading the code cannot narrow
  • Terabyte corpora: the context lives in one process's memory

Where the tokens go

Every agent pays a system prompt of about 1,000 tokens (4,070 chars ÷ 4), cached after the first agent on caching backends. Each turn re-sends the conversation; Claude Code and the Anthropic backend serve most of it from cache, which is why the OpenSSH run shows 6.8k of 11k input tokens cached. Cell output is capped at 8,000 chars per turn, so a model that prints carelessly cannot blow up the context. Sub-calls pay for exactly the data the code selected.

So the cost of a run scales with the number of turns and the amount of data the code chooses to read, not with the size of context. That is the real saving, and it is why a 3.7 MB file cost $0.0008 in the README's measurements.

Where the time goes

A turn through Claude Code takes 1 to 3 seconds with Haiku. The REPL is not the bottleneck: scanning 100 MB of text in a cell takes under a second. A 5-turn run is therefore 5 to 15 seconds before sub-calls. A single-call baseline would be one round trip.

What the research says

The paper rlm-ig implements (Zhang, Kraska and Khattab, arXiv:2512.24601) reports that RLMs handle inputs about two orders of magnitude beyond the model's window and beat base models and common long-context scaffolds on four long-context benchmarks, at comparable or lower median cost per query. Commentary on the paper reports that the cost distribution has a long tail: most queries are cheap, a few are several times more expensive.

A later reproduction (arXiv:2603.02615, "Think, But Don't Overthink") found RLMs slow and expensive in practice, with per-query latencies of 89 and 344 seconds in its settings, and found that going to depth 2 made models overthink and spawn excessive sub-calls. Another reading of the paper notes that the REPL-only ablation, with no sub-calls, already captures much of the gain on some tasks, which suggests the REPL matters more than the recursion for those.

My read: the REPL plus code-for-exact-work idea is the durable part. Deep recursion is the speculative part. rlm-ig's defaults lean on the durable part (batching, cheap sub-models, a pass-through guard) but still allow depth 2 by default, which the reproduction suggests is risky.

Fit

RAG, triage and small models

Can it replace RAG?

No, not in general. RAG answers "find the few relevant passages among millions" in milliseconds from a prebuilt index, and amortises indexing over many queries. rlm-ig has no index, explores per question, and holds the data in one process's memory.

They fit together. Give the model your retriever as a tool (the docstring example in tools/__init__.py is literally kb_search(query, k)) and let rlm-ig do the part RAG is bad at: counting, comparing and checking across the retrieved set. Where the whole relevant dataset fits in RAM (one customer's tickets, one incident's logs, one contract folder) and questions are aggregations, rlm-ig can replace a RAG pipeline you would otherwise have to build.

Can it do triage?

Batch triage, yes. Online triage, no. ask_map with a schema is a ready-made bulk classifier: the README's 300-ticket run got 296 right in 23 s for $0.028. That suits backlog sorting, weekly theme reports, and labelling data to train a cheaper classifier.

Classifying each ticket as it arrives is a single cheap call with a fixed prompt. Wrapping it in an agent loop adds turns and seconds for nothing. Use rlm-ig to find the categories and rules; use a plain call or a small model in the hot path.

Small or local models

I read "jev model" in your question as a small, cheap or local model; tell me if you meant something else. Ollama and any OpenAI-compatible server work out of the box (ollama:<model>).

The root model has to write correct Python every turn, and that is where small models struggle: the README notes Haiku sometimes replies without a code block or with a mangled one, which is why the repair code exists. The sensible split is a capable root and a small sub_model for ask_map reading work. The paper also reports a post-trained 8B model (based on Qwen3-8B) that was trained to work recursively, so small models can do this when trained for it.

Production

Enterprise and production use

Good fits share three traits: a bounded dataset that fits in memory, a question that code can mostly answer, and a tolerance for answers taking seconds to minutes.

Production checklist

  • Use an API backend for predictable billing and quotas. Claude Code under a subscription reports API-equivalent prices and is built for interactive use; check your plan's terms before running it unattended.
  • Run untrusted data with --sandbox docker, and make every tool read-only and argument-validated.
  • Always pass a schema so prose is never accepted as an answer, and call result.raise_for_status() or check exit codes (0, 2, 1) in pipelines.
  • Set max_usd, max_calls and timeout per job; treat partial as "needs review".
  • Decide trace retention; traces hold your data.
  • Size memory: about 200 MB per live Claude Code process, about 20 MB plus the context per REPL worker.
  • Prefer tasks whose answers code can verify, and log the trace path with every answer.

What has not been proven yet

  • The Anthropic and OpenAI-compatible backends were tested against local servers that speak the wire formats, not against the live services (README, Known limits).
  • The MCP client was tested against conformance fakes, not third-party servers.
  • opencode was not run end to end on a hosted provider.
  • Podman, native Windows and arm64 hardware are untested.
  • All measured numbers come from one sandbox with Claude Haiku as both root and sub-model. Larger models change latency and cost.
Critique

Weak points in the design

The codebase is careful and unusually well documented. These are the places I would push on before relying on it in production.

IssueWhy it mattersWhat I would change
Every ask on Claude Code starts a new CLI processClaudeCode does not override Model.complete(), so each sub-call creates a chat, spawns claude -p (about 200 MB), sends one message and closes it. Batching hides this for ask_map, but a loop of single ask calls pays start-up every time.A small pool of warm processes for one-shot calls, or route sub-calls to an API backend by default.
Default max_depth = 2The paper ran depth 1 and the reproduction reports depth 2 causes overthinking and runaway sub-calls. The pass-through guard covers only delegate, not delegate_map.Default to 1; make depth 2 opt-in.
Prose accepted as the answerTwo prose replies in a row become the final answer when there is no schema. A model asking a clarifying question twice ends the run with that question as the "answer".Mark such results partial, or require a schema in library use.
timeout is checked between callsOne long cell can overshoot; the hard stop is at timeout × 1.5 + 30.Fine for batch jobs; document it as soft for SLAs.
max_usd is only as good as the cost signalUnder a subscription it caps a hypothetical bill; on backends without cost or a price entry it does nothing (a note is emitted, not an error).Option to fail fast when max_usd is set and cost is unknown.
Data handed to sub-agents goes through JSONdelegate data is reduced with jsonable(), so non-JSON objects become their repr, and big slices cross the pipes twice (worker to host to child worker).Acceptable; worth a warning when a repr fallback happens.
Batching shares attentionUp to 16 items share one call; one confusing item can make the whole batch fail validation and fall back to 16 single calls.Split a failed batch in halves before going to singles.
Context lives in one processThe worker holds the whole context in RAM, and the host keeps it too so it can restart a crashed worker. There is no streaming or on-disk mode.A file-backed or memory-mapped context for very large inputs.
Lineage

Where the idea comes from

The repo cites two sources. The method comes from the Recursive Language Models paper by Alex L. Zhang, Tim Kraska and Omar Khattab (MIT CSAIL, arXiv:2512.24601). The example data comes from Loghub (Zhu et al., ISSRE 2023). The README states rlm-ig is an independent implementation, not affiliated with the authors.
